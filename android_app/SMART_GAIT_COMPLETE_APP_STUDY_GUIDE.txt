  - maxSdkVersion=30 means the old permissions are only declared for devices
    running Android 11 or lower.

2.1 ARCHITECTURE PATTERN: MVVM
-------------------------------

The app uses MVVM (Model-View-ViewModel):

  MODEL (Data layer):
    - Packets.kt         -> RiskPacket, LiveDataPacket, StatusPacket
    - Models.kt          -> AppState, ConnectionState, SessionSummary, Baseline
    - UserPreferences.kt -> DataStore-based authentication and profile

  VIEW (UI layer):
    - All files in ui/screens/  -> Composable functions
    - Components.kt, Charts.kt -> Reusable UI components
    - Theme files              -> Color, Typography, Theme

  VIEWMODEL (Logic layer):
    - MainViewModel.kt -> Holds AppState, handles user actions
    - Repository        -> Data source abstraction

  The ViewModel does NOT know about the UI.
  The UI observes the ViewModel's StateFlow using collectAsState().
  The ViewModel talks to the Repository, not directly to BLE or simulation.

2.3 HOW DATA FLOWS IN SIMULATION MODE (WHAT ACTUALLY RUNS)
-----------------------------------------------------------

[VERIFIED] Step-by-step from source code:

1. MainActivity creates MainViewModel via ViewModelProvider

2. MainViewModel constructor creates Repository() with default SimulationSource()

3. MainViewModel.init block calls repository.start() in a coroutine

4. Repository.start() does:
   - Sets connection state to CONNECTED
   - Launches a coroutine that calls simulation.packets().collect { ... }
   - For each RiskPacket received from simulation:
     a. Emits the RiskPacket via _risks flow
     b. DERIVES a LiveDataPacket from the risk values:
        - hr = 72 + physio * 0.4
        - temp = 36.6 + physio * 0.01
        - heel = 420 * (1 - imbalance * 0.25)    where imbalance = injury/100
        - forefoot = 310 * (1 + imbalance * 0.25)
        - acc = 1.21 (constant)
        - cad = 168 (constant)
        - mode = "SIMULATION"
     c. Emits a StatusPacket:
        - device = "SMART_GAIT_001"
        - firmware = "0.8.0"
        - battery = 97
        - connected = true
        - sensor_ready = false
        - mode = "SIMULATION"

5. MainViewModel collects all three flows in separate coroutines:
   - risks.collect -> updates AppState.risk and AppState.riskHistory (max 60 items)
   - lives.collect -> updates AppState.live and AppState.samples (max 60 items)
   - statuses.collect -> updates AppState.status

6. UI screens call vm.state.collectAsState() to get the latest AppState
   and display the values.


2.4 COROUTINES IN THE PROJECT
------------------------------

Coroutines are used for:
  1. SimulationSource: Uses flow { while(true) { emit(); delay(1000) } }
  2. Repository: Uses CoroutineScope(Dispatchers.Default).launch to collect
  3. MainViewModel: Uses viewModelScope.launch for each flow collector
  4. UserPreferences: All DataStore operations are suspend functions
  5. UI screens: Use rememberCoroutineScope() + scope.launch for login/signup

Key coroutine concepts used:
  - Flow: A cold asynchronous stream (SimulationSource.packets())
  - SharedFlow: A hot flow that can have multiple collectors (Repository flows)
  - StateFlow: A hot flow that always has a current value (AppState)
  - viewModelScope: Automatically cancelled when ViewModel is cleared
  - collect: Terminal operator that receives each emitted value


2.5 DEPENDENCY CREATION (NO DEPENDENCY INJECTION FRAMEWORK)
------------------------------------------------------------

The project does NOT use Hilt, Dagger, or Koin.

How dependencies are created:
  - MainViewModel default-constructs Repository() in its constructor parameter
  - Repository default-constructs SimulationSource() in its constructor parameter
  - UserPreferences is created manually in AppNavigation using context.dataStore
  - BleManager/GattDataSource are created manually (not used in simulation mode)

This is simple "manual dependency injection" through constructor parameters.

3.5 repository/SimulationSource.kt (29 lines)
-----------------------------------------------
[VERIFIED] Source file: repository/SimulationSource.kt

PURPOSE: Generates simulated risk data for testing without real hardware.

ENUM: SimulationScenario
  Values: SMOOTH, ELEVATED, ALERT

CLASS: SimulationSource
  Constructor parameters:
    - intervalMs: Long = 1000   (emit interval, default 1 second)
    - scenario: SimulationScenario = SMOOTH  (mutable property)

  Function: packets(): Flow<RiskPacket>
    Creates an infinite flow that emits one RiskPacket per intervalMs.

  Score calculation per scenario:
    SMOOTH:   score = 25 + (counter % 10) * 2     -> range: 25 to 43
    ELEVATED: score = 62 + (counter % 5) * 3      -> range: 62 to 74
    ALERT:    score = 90                           -> fixed at 90

  Risk level determination:
    score >= 70  -> "HIGH"
    score >= 40  -> "MODERATE"
    else         -> "LOW"

  The emitted RiskPacket includes:
    - injury = score
    - physio = min(score + 5, 100)
    - overall = min(score + 2, 100)
    - All three levels = same level
    - status = "SIMULATION"
    - alert = true when level is "HIGH"
    - alert_type = "BOTH" when HIGH, else "NONE"
    - message = "Simulated data; prototype risk estimation, not a diagnosis."

PURPOSE: The most complete BLE implementation. Full GATT data source with
permission checking, service discovery, notification subscription, and
command writing.

  Constructor: context: Context, device: BluetoothDevice

  Key features:
  1. Permission checking: Uses ContextCompat.checkSelfPermission() before
     every Bluetooth operation.

  2. connect(): Calls device.connectGatt(context, false, callback)

  3. BluetoothGattCallback implementation:
     a. onConnectionStateChange: On connect -> discoverServices().
        On disconnect -> emits error.
     b. onServicesDiscovered: Subscribes to NOTIFICATIONS on three
        characteristics: LIVE_DATA, RISK, STATUS.
        Uses the standard CCCD descriptor UUID: 00002902-0000-1000-8000-00805f9b34fb
        Writes ENABLE_NOTIFICATION_VALUE to each descriptor.
     c. onCharacteristicChanged: Emits Pair<UUID, ByteArray>
     d. onCharacteristicRead: Emits Pair<UUID, ByteArray> on success

  4. writeCommand(): Encodes BleCommand to JSON using CommandCodec,
     writes to COMMAND characteristic.

  NOTE: GattDataSource is NOT currently used by the running app.
  The Repository class uses SimulationSource instead. GattDataSource is
  the class that WOULD be used when connecting to real hardware.

  3. Collect repository.statuses -> update AppState.status
  4. Collect repository.connection -> update AppState.connection

  command(command: BleCommand):
    Routes commands to appropriate handler:
    - START_SESSION -> startMonitoring()
    - STOP_SESSION -> stopMonitoring()
    - START_CALIBRATION or CALIBRATE -> calibrate()
    - Others -> repository.sendCommand()

  startMonitoring():
    - Guards: if already monitoring, return
    - Sets monitoring=true, records sessionStartedAt, message="Monitoring active"
    - Sends START_SESSION to repository

  stopMonitoring():
    - Guards: if not monitoring, return
    - Creates SessionSummary from current samples and riskHistory
    - Summary includes: averages of HR/temp/cadence, peaks of risk scores,
      final risk level
    - Adds summary to history (max 20 sessions)
    - Sets monitoring=false, message="Session complete"
    - Sends STOP_SESSION to repository

  calibrate():
    - Guards: if already calibrating, return
    - Sets calibrating=true, progress=0
    - Simulates calibration: repeats 5 times with 400ms delay, incrementing
      progress by 20% each time
    - After completion: takes last 10 samples, averages HR, temp, heel, forefoot
      to create Baseline
    - Sets calibrating=false, stores baseline
    - Sends START_CALIBRATION to repository

  scenario(s: SimulationScenario):
    - Calls repository.selectScenario(s)
    - Updates _selectedScenario
    - Sets message like "Smooth simulation selected"

  markStale(now, timeout=5000):
    - Marks risk data as stale if it's older than timeout milliseconds

  selectSession(session): Sets _selectedSession
  clearMessage(): Sets message to null

  onCleared(): Stops repository when ViewModel is destroyed

PHASE 5 — BLE / SENSOR COMMUNICATION PATH
================================================================================

5.1 OVERVIEW
-------------

The BLE communication is designed but NOT actively used in the current running
app. The app runs in SIMULATION mode by default.

However, the BLE code is complete and ready for real hardware. Here is the
full intended BLE path:

5.2 SCAN -> CONNECT -> GATT -> PARSE -> MODEL -> UI
------------------------------------------------------

STEP 1: SCAN
  Class: BleScanner
  - Uses BluetoothAdapter.getBluetoothLeScanner()
  - Creates ScanFilter for device name "SMART_GAIT_001"
  - Sets scan mode to LOW_LATENCY
  - When device is found: calls onDevice callback with ScanResult

STEP 2: CONNECT
  Class: BleConnection (or BleManager.connect())
  - Calls device.connectGatt(context, false, callback)
  - autoConnect = false (connect immediately, don't wait)
  - On STATE_CONNECTED callback: calls discoverServices()

STEP 3: GATT SERVICE DISCOVERY
  Class: GattDataSource (most complete implementation)
  - onServicesDiscovered callback fires
  - Gets the Smart Gait service using SERVICE UUID (7e3a0001-...)
  - For each characteristic (LIVE_DATA, RISK, STATUS):
    a. Gets the characteristic from the service
    b. Calls setCharacteristicNotification(characteristic, true)
    c. Gets the CCCD descriptor (UUID 00002902-0000-1000-8000-00805f9b34fb)
    d. Writes ENABLE_NOTIFICATION_VALUE to the descriptor
  - This tells the ESP32 to push data whenever it changes

STEP 4: RECEIVE DATA
  - onCharacteristicChanged callback fires when ESP32 sends data
  - Emits Pair<UUID, ByteArray> via SharedFlow

STEP 5: PARSE
  Class: PacketParser
  - Determines packet type by checking UUID:
    - RISK UUID -> PacketParser.risk(bytes) -> RiskPacket
    - LIVE_DATA UUID -> PacketParser.live(bytes) -> LiveDataPacket
    - STATUS UUID -> PacketParser.status(bytes) -> StatusPacket
  - JSON format: {"type":"risk","injury":45.2,...}

STEP 6: MODEL
  Class: Repository
  - Emits parsed packets to SharedFlow channels
  - ViewModel collects and updates AppState

STEP 7: UI
  - Screens call vm.state.collectAsState()
  - Compose automatically recomposes when state changes

5.3 SEND COMMANDS (APP -> ESP32)
----------------------------------

  1. UI calls vm.command(BleCommand.PING) (or START_SESSION, etc.)
  2. MainViewModel routes to repository.sendCommand()
  3. Repository calls GattDataSource.writeCommand()
  4. GattDataSource uses CommandCodec.encode(command.wire) to get JSON string
     Example: {"command":"PING"}
  5. Writes JSON bytes to the COMMAND characteristic (7e3a0005-...)
  6. ESP32 receives and processes the command

6.1 IMPORTANT DISCLAIMER
--------------------------

In this app, the risk calculation does NOT happen on the Android phone.
The risk scores are computed by the ESP32 firmware and sent as numbers
in the RiskPacket. The Android app DISPLAYS the risk values; it does not
calculate them.

However, the SimulationSource generates simulated scores, and the app
determines the risk LEVEL from the score.

6.3 SIMULATION SCORE GENERATION (line by line walkthrough)
-----------------------------------------------------------

[VERIFIED] Source: SimulationSource.kt lines 8-27

  fun packets(): Flow<RiskPacket> = flow {
    var i = 0                             // Counter variable
    while (true) {                        // Infinite loop
      val score = when (scenario) {
        SMOOTH ->                         // Low risk scenario
          25f + (i++ % 10) * 2f           // 25, 27, 29, 31, ..., 43, 25, 27, ...
        ELEVATED ->                       // Moderate risk scenario
          62f + (i++ % 5) * 3f            // 62, 65, 68, 71, 74, 62, 65, ...
        ALERT ->                          // High risk scenario
          90f                             // Fixed at 90
      }

WORKED EXAMPLE (SMOOTH scenario):

  When i=0:  score = 25 + (0 % 10) * 2 = 25 + 0  = 25.0  -> level = "LOW"
  When i=1:  score = 25 + (1 % 10) * 2 = 25 + 2  = 27.0  -> level = "LOW"
  When i=2:  score = 25 + (2 % 10) * 2 = 25 + 4  = 29.0  -> level = "LOW"
  ...
  When i=7:  score = 25 + (7 % 10) * 2 = 25 + 14 = 39.0  -> level = "LOW"
  When i=8:  score = 25 + (8 % 10) * 2 = 25 + 16 = 41.0  -> level = "MODERATE"
  When i=9:  score = 25 + (9 % 10) * 2 = 25 + 18 = 43.0  -> level = "MODERATE"
  When i=10: score = 25 + (0 % 10) * 2 = 25 + 0  = 25.0  -> level = "LOW" (resets)

  So SMOOTH cycles between 25 and 43, crossing into MODERATE briefly.

WORKED EXAMPLE (ELEVATED scenario):

  i=0: score = 62 + (0 % 5) * 3 = 62.0  -> "MODERATE"
  i=1: score = 62 + (1 % 5) * 3 = 65.0  -> "MODERATE"
  i=2: score = 62 + (2 % 5) * 3 = 68.0  -> "MODERATE"
  i=3: score = 62 + (3 % 5) * 3 = 71.0  -> "HIGH"
  i=4: score = 62 + (4 % 5) * 3 = 74.0  -> "HIGH"
  i=5: score = 62 + (0 % 5) * 3 = 62.0  -> "MODERATE" (resets)

  So ELEVATED cycles between 62 and 74, moving between MODERATE and HIGH.

8.1 JETPACK COMPOSE BASICS
----------------------------

Jetpack Compose is Android's modern UI toolkit. Instead of XML layouts,
you write UI as Kotlin functions annotated with @Composable.

In this project:
  - Every screen is a @Composable function (not an Activity or Fragment)
  - UI automatically updates when state changes (reactive)
  - No XML layout files (except styles.xml for the base Android theme)

Example from DashboardScreen:
  @Composable
  fun DashboardScreen(state: AppState, userProfile: UserProfile, modifier: Modifier) {
      LazyColumn(...) {
          item { RiskGauge(score = risk?.overall ?: 0f, ...) }
      }
  }

When state.risk changes, Compose automatically recomposes (redraws) the
affected parts of the UI.


8.2 STATE MANAGEMENT WITH STATEFLOW
--------------------------------------

StateFlow is a Kotlin coroutines concept. It holds a single value and
notifies all collectors when the value changes.

  In MainViewModel:
    private val _state = MutableStateFlow(AppState(simulation=true))
    val state: StateFlow<AppState> = _state.asStateFlow()

  In UI:
    val state by vm.state.collectAsState()

  collectAsState() converts the StateFlow into Compose State,
  which triggers recomposition when the value changes.


8.3 NAVIGATION IN COMPOSE
---------------------------

The app uses Jetpack Navigation Compose:
  - NavHost defines all routes (composable("route") { ... })
  - navController.navigate("route") navigates to a screen
  - popUpTo("route") { inclusive = true } removes screens from back stack
  - rememberNavController() creates the NavController

The bottom navigation uses manual selectedTab state (not NavHost routes).
Each tab shows a different Composable within the same "main" route.


8.4 LAZYCOLUMN
----------------

LazyColumn is Compose's equivalent of RecyclerView. It efficiently
renders only the visible items on screen.

Every main screen uses LazyColumn:
  LazyColumn(contentPadding = PaddingValues(...), verticalArrangement = ...) {
      item { Header() }            // Single item
      items(list) { item -> ... }  // List of items
  }

8.8 MODIFIER CHAIN

==== CATEGORY A: PROJECT OVERVIEW (10 questions) ====

Q1: What is the project name and what does it do?

   physiological metrics (heart rate, temperature), and provides early risk
   estimation for potential injuries.

Q2: What hardware does the system use?
A: ESP32 microcontroller with 2 FSR sensors (heel + forefoot), MPU6050
   accelerometer/gyroscope, MAX30102 pulse oximeter (heart rate), MAX30205
   temperature sensor, and a vibration motor for haptic alerts.

Q3: What platform and language is the app built on?
A: Android platform using Kotlin language and Jetpack Compose UI framework.

Q4: What is the app's package name and application ID?
A: com.idp.smartgait

Q5: What Android versions does the app support?
A: minSdk 26 (Android 8.0 Oreo) to targetSdk/compileSdk 35 (Android 15).

Q6: Is this a medical diagnostic tool?
A: No. It provides "risk estimation" and "early warning" for abnormal
   patterns. Every screen includes a disclaimer: "Prototype risk estimation -
   not a medical diagnosis."

Q7: What mode does the app currently run in?
A: Simulation mode. The app generates fake sensor data every 1 second using
   SimulationSource. Real BLE hardware code is written but not actively used.

Q8: How many screens does the app have?
A: 13 new screens (splash, onboarding, login, signup, forgot password,
   profile setup, dashboard, live, gait, history, physiological, profile,
   settings) plus 1 old screen file (Screens.kt, unused dead code).

Q9: What is the risk scoring range?
A: 0 to 100. LOW = 0-39 (green), MODERATE = 40-69 (amber), HIGH = 70-100 (red).

Q10: What communication protocol is used between ESP32 and Android?
A: Bluetooth Low Energy (BLE) with JSON-formatted data over GATT characteristics.


==== CATEGORY B: ARCHITECTURE (10 questions) ====

Q11: What architecture pattern does the app use?
A: MVVM (Model-View-ViewModel). The Model layer includes data classes and
   repository. The View layer is Compose UI. The ViewModel holds AppState.

Q12: What is the central state object?
A: AppState (in data/Models.kt). It contains connection state, risk data,
   live sensor data, status, simulation flag, monitoring state, session
   history, samples, baseline, calibration progress, and messages.

Q13: How does data flow from simulation to UI?
A: SimulationSource -> Repository (via Flow<RiskPacket>) -> MainViewModel
   (collects and updates StateFlow<AppState>) -> UI screens (collectAsState()).

Q14: Does the app use dependency injection?
A: No DI framework (no Hilt, Dagger, or Koin). Dependencies are created via
   constructor parameters with default values (manual DI).

Q15: How does the ViewModel communicate with the Repository?
A: Through the RiskRepository interface using Kotlin Flow. The ViewModel
   collects Flow emissions and updates its StateFlow<AppState>.

Q16: What is the RiskRepository interface?
A: It defines: risks, lives, statuses (Flow properties), connection (Flow),
   start(), stop(), sendCommand(), and selectScenario() functions.

Q17: How is the ViewModel created?
A: In MainActivity via ViewModelProvider(this)[MainViewModel::class.java].
   ViewModelProvider uses the default factory which calls the no-arg constructor.

Q18: Why does MainViewModel have a default parameter for Repository?
A: So it can be constructed without arguments by ViewModelProvider (which calls
   the no-arg constructor), while still allowing test code to inject a mock.

Q19: How many StateFlows does MainViewModel maintain?
A: Three: _state (AppState), _selectedScenario (SimulationScenario),
   _selectedSession (SessionSummary?).

Q20: What happens when MainViewModel is cleared?
A: onCleared() calls repository.stop() to cancel the simulation coroutine,
   then calls super.onCleared().


==== CATEGORY C: KOTLIN AND COROUTINES (10 questions) ====

Q21: What are coroutines?
A: Lightweight threads in Kotlin for asynchronous programming. They allow
   writing non-blocking code that looks sequential. Used throughout this
   app for data flow and background operations.

Q22: What is a Flow in Kotlin?
A: A cold asynchronous stream that emits values over time. Cold means it
   doesn't start producing until someone collects it. SimulationSource.packets()
   returns a Flow<RiskPacket>.

Q23: What is a SharedFlow?
A: A hot Flow that can have multiple collectors. The Repository uses
   MutableSharedFlow for risks, lives, and statuses so that multiple
   ViewModels or collectors can receive the same data.

Q24: What is a StateFlow?
A: A hot Flow that always holds a current value and emits updates. It's like
   SharedFlow with a replay of 1. AppState is held in a StateFlow.

Q25: What is viewModelScope?
A: A CoroutineScope tied to the ViewModel's lifecycle. All coroutines launched
   in viewModelScope are automatically cancelled when the ViewModel is cleared.

Q26: What does collectAsState() do?
A: Converts a Kotlin Flow or StateFlow into a Compose State object. When the
   Flow emits a new value, Compose recomposes the affected UI.

Q27: What is the delay() function?
A: A suspend function that pauses a coroutine for a specified time without
   blocking the thread. Used in SimulationSource (1000ms) and calibration (400ms).

Q28: What does .coerceIn(min, max) do?
A: Constrains a value to be within [min, max]. Example: (injury/100f).coerceIn(0f,1f)
   ensures the result is between 0 and 1.

Q29: What is runCatching { }.getOrNull()?
A: Runs a block of code and catches any exception. If successful, returns the
   result. If an exception occurs, returns null. Used in PacketParser to safely
   parse JSON without crashing.

Q30: What is the difference between launch and collect?
A: launch starts a new coroutine. collect is a terminal Flow operator that
   receives each emitted value. You typically launch { flow.collect { ... } }.


==== CATEGORY D: JETPACK COMPOSE (10 questions) ====

Q31: What is Jetpack Compose?
A: Android's modern declarative UI toolkit. You describe what the UI should look
   like using Kotlin functions, and Compose handles the rendering and updates.

Q32: What is a @Composable function?
A: A function annotated with @Composable that can emit UI elements. It cannot
   be called from regular functions, only from other Composable functions.

Q33: What is recomposition?
A: When a Composable's input (state) changes, Compose re-executes that function
   to update the UI. Only affected parts are re-rendered, not the entire screen.

Q34: What does remember { } do?
A: Remembers a value across recompositions. Without remember, the value would be
   reset every time the Composable re-executes.

Q35: What does mutableStateOf() do?
A: Creates a Compose State object that triggers recomposition when its value
   changes. Used with remember for local UI state (e.g., text fields).

Q36: What is a LazyColumn?
A: A vertically scrolling list that only renders visible items on screen.
   Similar to RecyclerView but declarative. Every main screen uses LazyColumn.

Q37: What is Modifier in Compose?
A: An object that modifies the layout, appearance, or behavior of a Composable.
   Modifiers are chained: Modifier.fillMaxSize().padding(16.dp).background(color).

Q38: What is LaunchedEffect?
A: A side-effect handler in Compose. Code inside LaunchedEffect runs once when
   the key changes (or on first composition). Used for one-time operations.

Q39: What is a Scaffold?
A: A Material 3 layout structure that provides slots for top bar, bottom bar,
   FAB, snackbar, and content. The app uses Scaffold with a bottom NavigationBar.

Q40: How does bottom navigation work in this app?
A: A selectedTab integer state tracks the current tab. NavigationBar with
   NavigationBarItem for each tab. When clicked, selectedTab changes, and a
   when(selectedTab) block shows the corresponding screen Composable.


==== CATEGORY E: BLE (BLUETOOTH LOW ENERGY) (10 questions) ====

Q41: What is BLE?
A: Bluetooth Low Energy, a power-efficient wireless protocol for short-range
   communication. Used by IoT devices to send small amounts of data to phones.

Q42: What is GATT?
A: Generic Attribute Profile - the standard BLE communication protocol.
   Data is organized into Services (groups) containing Characteristics (data points).

Q43: What UUIDs does this project use?
A: Custom UUIDs:
   Service:   7e3a0001-5e8d-4f4a-9a9b-1a2b3c4d5e01
   Live Data: 7e3a0002-5e8d-4f4a-9a9b-1a2b3c4d5e01
   Risk:      7e3a0003-5e8d-4f4a-9a9b-1a2b3c4d5e01
   Status:    7e3a0004-5e8d-4f4a-9a9b-1a2b3c4d5e01
   Command:   7e3a0005-5e8d-4f4a-9a9b-1a2b3c4d5e01

Q44: What is the BLE device name?
A: "SMART_GAIT_001" (defined in BleUuids.kt).

Q45: How does the app scan for BLE devices?
A: BleScanner uses BluetoothAdapter.getBluetoothLeScanner().startScan() with
   a ScanFilter that filters by device name "SMART_GAIT_001".

Q46: What is a CCCD descriptor?
A: Client Characteristic Configuration Descriptor (UUID 00002902-0000-1000-8000-
   00805f9b34fb). Writing ENABLE_NOTIFICATION_VALUE to it tells the BLE device
   to push data updates to the phone automatically.

Q47: How does the app receive data from ESP32?
A: After subscribing to notifications, the ESP32 sends data through BLE
   characteristic changes. The onCharacteristicChanged callback is triggered,
   and the byte array is emitted via SharedFlow.

Q48: How are commands sent to the ESP32?
A: CommandCodec.encode() serializes the command to JSON (e.g., {"command":"PING"}),
   which is converted to bytes and written to the COMMAND characteristic.

Q49: Why does the app need BLUETOOTH_CONNECT permission?
A: To connect to a BLE device and communicate with it. Android 12+ requires
   this specific permission instead of the older BLUETOOTH permission.

Q50: Why is BLE not used in the running app?
A: The Repository class uses SimulationSource by default. To use real BLE,
   you would need to replace SimulationSource with GattDataSource integration.

Q59: What are the three simulation scenarios?
A: SMOOTH (low risk, 25-43), ELEVATED (moderate-high, 62-74), ALERT (high, 90).

Q60: How often does simulation emit data?
A: Every 1000 milliseconds (1 second), configurable via intervalMs parameter.

Q61: How is the SMOOTH score calculated?
A: score = 25 + (counter % 10) * 2, cycling from 25 to 43.

Q62: How does the simulation generate sensor readings?
A: Repository derives them from risk scores. Heart rate = 72 + physio*0.4,
   Temperature = 36.6 + physio*0.01, Heel/Forefoot based on imbalance ratio.

Q63: Is simulation data labeled?
A: Yes. The status field is "SIMULATION" and mode is "SIMULATION" in all
   simulated packets.

Q64: How do you change simulation scenario?
A: Call vm.scenario(SimulationScenario.ELEVATED). This calls
   repository.selectScenario() which sets simulation.scenario property.
   The UI has FilterChips on the Live screen for this.

Q65: Does the counter reset when scenario changes?
A: No. The counter (i) continues incrementing. Only the score formula changes.

Q66: What does the simulation return for battery?
A: Always 97% (hardcoded in Repository.start() StatusPacket).

Q72: Can the user go back to login after reaching main?

Q73: What are the bottom navigation tabs?

==== CATEGORY M: MONITORING AND SESSIONS (8 questions) ====

Q107: How does monitoring start?
A: Call vm.startMonitoring(). It sets monitoring=true, records
   sessionStartedAt, shows "Monitoring active" message, and sends
   START_SESSION command to repository.

Q108: How does monitoring stop?
A: Call vm.stopMonitoring(). It creates a SessionSummary from current
   samples and riskHistory, adds it to history, sets monitoring=false,
   and sends STOP_SESSION command.

Q109: What does a SessionSummary contain?
A: Start/end timestamps, average HR/temp/cadence (nullable), peak overall/
   injury/physio risk scores, and final risk level string.

Q110: How are averages calculated?
A: Using a private extension List<Float>.averageOrNull() which returns null
   for empty lists and average().toFloat() otherwise. Applied to HR, temp,
   and cadence values from LiveDataPacket samples.

Q111: How many sessions are kept?
A: Maximum 20, using (history + summary).takeLast(20).

Q112: Is session history persisted?
A: No. Session history is in-memory only (part of AppState StateFlow).
   Lost when app closes.

Q113: What does calibration do?
A: Simulates 5 steps of 400ms each (2 seconds total), averaging the last
   10 sensor samples to create a Baseline (HR, temp, heel, forefoot).

Q114: What is the Baseline used for?
A: Displayed on the Settings and Physiological screens as reference values.
   The app shows delta (difference) between current and baseline values.

==== CATEGORY O: KOTLIN LANGUAGE FEATURES (10 questions) ====

Q121: What is a data class?
A: A Kotlin class that automatically generates equals(), hashCode(), toString(),
   copy(), and componentN() functions. All models use data class.

Q122: What is an enum class?
A: A type-safe way to define a fixed set of constants. ConnectionState and
   SimulationScenario are enum classes.

Q123: What is an object declaration?
A: A singleton pattern in Kotlin. PacketParser, CommandCodec, and BleUuids
   are object declarations - only one instance exists.

Q124: What is a companion object?
A: A static-like member of a class. UserPreferences has a private companion
   object holding the DataStore key constants.

Q125: What does the ?.let { } pattern do?
A: Safe call + scope function. If the value is non-null, executes the block
   with the value as "it". Example: descriptor?.let { g.writeDescriptor(it) }

Q126: What does takeIf { } do?
A: Returns the value if the predicate is true, null otherwise. Used in
   PacketParser: decodeFromString<RiskPacket>(...).takeIf { it.type == "risk" }

Q127: What are default parameter values?
A: Function/constructor parameters with default values. Example:
   RiskPacket(type: String = "risk", ts: Long = 0, ...) - all fields have defaults.

Q128: What is a sealed class / when expression?
A: when is Kotlin's replacement for switch statement. Used throughout for
   risk level determination, navigation routing, and command dispatch.

Q129: What is the by keyword in Kotlin?
A: Delegation. Used for:
   - Property delegation: val state by vm.state.collectAsState()
   - DataStore delegation: val Context.dataStore by preferencesDataStore(...)

Q130: What is an extension function?
A: A function added to an existing class without modifying it.
   Float.fmt() and List<Float>.averageOrNull() are extension functions.


==== CATEGORY P: ANDROID FUNDAMENTALS (10 questions) ====

Q131: What is an Activity?
A: A single screen in an Android app. This app has only one Activity
   (MainActivity). All visual screens are Composable functions.

Q132: What is a ViewModel?
A: A lifecycle-aware component that survives configuration changes
   (like screen rotation). MainViewModel holds app state.

Q133: What is the Android lifecycle?
A: The sequence of states an Activity goes through: Created -> Started ->
   Resumed -> Paused -> Stopped -> Destroyed. ViewModel survives until
   the Activity is permanently destroyed.

Q134: What is an Intent?
A: A messaging object for communication between Android components.
   The manifest declares an intent-filter with MAIN/LAUNCHER, making
   MainActivity the entry point.

Q135: What is AndroidManifest.xml?
A: The app's configuration file declaring activities, permissions, features,
   and other metadata. Required for every Android app.

Q136: What is the R class?
A: Auto-generated class providing IDs for resources (layouts, strings, etc.).
   This app barely uses it since Compose doesn't need XML layouts.

Q137: What is the difference between compileSdk and targetSdk?
A: compileSdk (35) = the API version used to compile. targetSdk (35) = the
   API version the app is designed for. minSdk (26) = minimum supported.

Q138: What is ViewModelProvider?
A: A class that creates and retrieves ViewModel instances with proper lifecycle
   management. Used in MainActivity to get MainViewModel.

Q139: What is setContent { }?
A: ComponentActivity function that sets the Compose UI tree as the activity's
   content. Replaces setContentView(R.layout.xxx) from XML-based apps.

Q140: What is an APK?
A: Android Package Kit - the installable file format for Android apps.
   Built using assembleDebug or assembleRelease Gradle tasks.

==== CATEGORY R: ERROR HANDLING (6 questions) ====

Q147: How does the app handle BLE errors?
A: All BLE calls are wrapped in try-catch(SecurityException).
   GattDataSource emits error strings via SharedFlow.

Q148: How does the app handle JSON parsing errors?
A: PacketParser uses runCatching { }.getOrNull(), returning null instead
   of crashing on malformed JSON.

Q149: What happens if BLE connection drops?
A: onConnectionStateChange with STATE_DISCONNECTED triggers error emission.
   ConnectionState updates to DISCONNECTED.

Q150: Does the app show error messages to the user?
A: Yes, via AppState.message which is shown as a Snackbar in the main app
   scaffold. Also, login errors are shown inline in the LoginScreen.

Q151: What happens if sensor data is stale?
A: MainViewModel.markStale() sets risk.stale=true if data is older than
   5 seconds. [INFERRED: UI could show stale indicator, but currently unused]

Q152: How does the app handle permission denial?
A: BLE operations catch SecurityException and fail silently or emit error
   messages. The app continues to function in simulation mode.


==== CATEGORY S: DESIGN DECISIONS (8 questions) ====

Q153: Why use Kotlin instead of Java?
A: Kotlin is the recommended language for Android development. It offers
   null safety, data classes, coroutines, and more concise syntax.

Q154: Why use Compose instead of XML layouts?
A: Compose is the modern Android UI toolkit. It offers declarative UI,
   automatic state management, less boilerplate, and better Kotlin integration.

Q155: Why use StateFlow instead of LiveData?
A: StateFlow is part of Kotlin coroutines, works naturally with Flow,
   and is not Android-specific (testable without Android dependencies).

Q156: Why single Activity architecture?
A: Modern Android best practice. All navigation is handled by Compose
   Navigation. Avoids the complexity of multiple Activities and Fragments.

Q157: Why DataStore instead of SharedPreferences?
A: DataStore is asynchronous (uses coroutines), type-safe, and handles
   data migration. SharedPreferences is synchronous and can cause ANRs.

Q158: Why not use Room database?
A: The app only needs to persist simple key-value pairs (auth/profile).
   Room would be overkill. Session history is intentionally in-memory only
   for this prototype. [INFERRED]

Q159: Why does the app have both BLE code and simulation?
A: Simulation allows development and testing without hardware. The BLE code
   is ready for when real hardware is connected. Both coexist through the
   RiskRepository interface.

Q160: Why are sensor readings in LiveDataPacket nullable (Float?)?
A: Because real sensors may not always provide readings. If a sensor fails
   or hasn't initialized, the value is null rather than 0 (which could be
   confused with a real reading).


==== CATEGORY T: ADVANCED TOPICS (8 questions) ====

Q161: What is kotlinx.serialization and how does it work?
A: A Kotlin compiler plugin that generates serialization code at compile time.
   Classes annotated with @Serializable get auto-generated serializers.
   Unlike Gson, it doesn't use reflection, making it faster.

Q162: How does the Compose BOM work?
A: Bill of Materials defines compatible versions for all Compose libraries.
   You declare the BOM platform, then add individual libraries without versions.
   Gradle resolves compatible versions automatically.

Q163: What is the CCCD (Client Characteristic Configuration Descriptor)?
A: A standard BLE descriptor (UUID 00002902-...) that controls notifications.
   Writing 0x0001 enables notifications, 0x0000 disables them. Essential for
   receiving push updates from BLE devices.

Q164: How does the Compose navigation back stack work?
A: NavController maintains a stack of routes. navigate() pushes a new route.
   popBackStack() pops the current route. popUpTo("route") { inclusive = true }
   pops everything up to and including that route.

Q165: What is the difference between MutableStateFlow and MutableSharedFlow?
A: StateFlow always has a current value (like a variable that can be observed).
   SharedFlow doesn't have a current value by default; it only emits events.
   StateFlow conflates - if you emit faster than collectors can process,
   intermediate values are dropped.

Q166: How does @SuppressLint("MissingPermission") work?
A: It suppresses the lint warning about missing Bluetooth permission checks.
   The actual permission check is done manually in the code (or in GattDataSource,
   using the allowed() helper function).

Q167: What is extraBufferCapacity in SharedFlow?
A: The number of values that can be buffered before tryEmit returns false.
   The BLE flows use extraBufferCapacity=1 (minimal buffer) and packet flows
   use 16 (larger buffer for BLE data).

Q168: What is a Protocol Buffer (.pb) file?
A: The binary format used by DataStore Preferences to store data on disk.
   It's more efficient than JSON/XML and is read/written by the DataStore
   library automatically.
