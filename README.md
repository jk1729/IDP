# Smart Gait Monitoring and Early Injury-Risk Detection System

This repository contains the Phase 1 software architecture for the two-FSR smart insole.
It is intentionally hardware-independent: the simulator and a future ESP32 adapter must
both produce the same `RawSensorData` record.

The current implementation includes:

- canonical raw and processed data models
- simulated heel/forefoot FSR, MPU6050, heart-rate, and temperature readings
- filtering and feature extraction
- 2-5 minute personal-baseline calibration
- prototype injury-risk and physiological-risk engines
- JSON and CSV export
- JSON schemas under `data/schemas/`

The values generated by the simulator are **SIMULATED DATA**, not experimental results.
FSR values remain raw ADC/relative values and are not converted to Newtons.

## Run Phase 1

From the repository root:

```text
python -m analytics.main
```

This creates:

- `data/simulated/session.jsonl`
- `data/simulated/session.csv`
- `data/simulated/example_reading.json`

The project uses only the Python standard library at this stage.

## Architecture

```text
simulator or future ESP32 adapter
              ↓
       RawSensorData
              ↓
          filtering
              ↓
    ProcessedSensorData
              ↓
       baseline comparison
              ↓
       risk engines
              ↓
          RiskResult
              ↓
  JSON/CSV → Android/database/Python analytics
```

The acquisition layer is the only layer that should change when real hardware is
introduced. Feature definitions, baseline fields, risk fields, JSON, CSV, and database
contracts should remain stable.

## Phase 8 ESP32/BLE scaffold

The [`esp32_firmware/`](D:/IDP/esp32_firmware/) directory contains a separate
PlatformIO/Arduino firmware scaffold. It provides the hardware-independent sensor
interface, simulated ESP32 readings, compact JSON BLE packets, device state, command
acknowledgements, and vibration-controller abstraction. The risk notification currently
uses an explicitly marked demo packet; injury and physiological risk are not calculated
inside firmware. PlatformIO compilation and physical BLE, sensor, battery, and motor
validation remain pending until the required hardware and PlatformIO environment are
available.

## Phase 3 sensor processing

Run the hardware-independent processing pipeline:

```text
python -m processing.main
```

It reads the Phase 2 CSV, filters both FSR channels and IMU magnitudes, calculates
loading distribution, detects prototype step events, estimates cadence/contact,
summarizes impact/angular motion, and filters heart rate and temperature. It writes
`data/processed/processed_data.csv`.

The processing layer receives CSV/data records and does not import simulator sensor
modules, so a future ESP32 adapter can provide the same fields. FSR values remain
relative ADC-like values. Dynamic acceleration uses `abs(filtered_acceleration - 9.81)`
because the simulator uses m/s². Step and gait-cycle values are prototype software
estimates, not clinical measurements.

Phase 3 deliberately does not implement injury risk, dehydration risk, baseline
calibration, BLE, Android, databases, hardware communication, or machine learning.

## Phase 4 personal baseline and calibration

Build an athlete-specific baseline from processed data:

```text
python -m baseline.main --input data/processed/processed_data.csv --athlete-id ATHLETE_001
```

The baseline stores mean, population standard deviation, minimum, maximum, and count
for available loading, gait, motion, heart-rate, and temperature features. Walking
rows are preferred for gait features, while REST rows are preferred for physiological
features. Missing and non-finite values are skipped; insufficient data produces an
error. The optional outlier rule removes values beyond four population standard
deviations before final statistics are calculated.

Current session values are compared with the baseline using absolute deviation,
percentage deviation, and z-score. A zero or near-zero standard deviation safely
produces a z-score of zero. This phase does not classify risk.

Use `--current-input` to compare a separate processed session:

```text
python -m baseline.main --input data/processed/baseline_session.csv \
  --current-input data/processed/current_session.csv
```

Optional distributions can be plotted with `baseline.visualize.plot_baseline_distributions`.
Plots are labelled `SIMULATED BASELINE - NOT CLINICAL DATA`.

The baseline is a software prototype and is not a medically validated reference.
Simulated data is not experimental or clinical data. No injury diagnosis, dehydration
diagnosis, machine learning, BLE, Android, database, or hardware communication is
implemented.

## Phase 5 injury-risk estimation

Run the prototype engine after creating a baseline:

```text
python -m injury_risk.main
```

The engine compares current processed features with the personal baseline and produces
four bounded components:

```text
pressure/loading deviation: 0.35
gait-motion deviation:      0.25
impact deviation:           0.20
gait-cycle abnormality:     0.20
```

The weighted score is clamped to 0-100 and classified as `LOW`, `MODERATE`, or `HIGH`
using configurable prototype thresholds. Signals explain abnormal loading, motion,
impact, or gait-cycle deviations. A persistence tracker requires consecutive abnormal
cycles before `vibration_alert` can become true; this is only a decision output and
does not control hardware.

The weighting and thresholds are prototype assumptions and are not clinically
validated. The system estimates abnormal gait/loading patterns and does not diagnose
injury. Phase 5 does not implement physiological/dehydration risk, BLE, Android,
database, hardware communication, or machine learning.

An optional component plot is available through
`injury_risk.visualize.plot_risk_result`. It is labelled
`SIMULATED DATA - PROTOTYPE RISK ESTIMATION` and is not an accuracy or clinical
prediction plot.

## Phase 6 physiological/dehydration-risk estimation

Build a 2-5 minute resting physiological baseline:

```text
python -m physiological.main `
  --baseline-input data/processed/physiological_baseline.csv `
  --current-input data/processed/processed_data.csv
```

The engine calculates personalized HR and temperature deviations:

```text
delta_hr = current_hr - resting_hr_base
delta_temperature = current_temperature - resting_temperature_base
raw_score = (delta_hr * 2) + (delta_temperature * 20)
```

The raw score and clamped `0-100` score are both retained. It also reports trends,
activity context, explanatory signals, persistence across high-risk windows, and an
`alert_requested` decision. The physiological engine remains independent from the
injury-risk engine and never controls hardware.

Heart rate and temperature are influenced by exercise intensity, environment, fitness,
sensor error and other factors. This prototype provides a dehydration-risk estimate
and does not diagnose dehydration. The prototype heuristic has not been clinically
validated. Simulated data is not experimental or clinical data.

## Phase 7 unified risk and alert engine

Run the pure-Python unified decision layer:

```text
python -m risk.main
```

The injury and physiological engines remain independent. The unified layer preserves
both scores and uses the maximum score for `overall_risk_score`; it never averages the
two values. `NORMAL` means both risks are low, `CAUTION` means a non-persistent
moderate/high concern exists, and `ALERT` requires a HIGH risk with persistence from
the corresponding engine.

The output includes source-labelled signals, alert type, software notification
priority, cooldown-aware `vibration_request`, alert state, transition events, and an
Android/hardware-ready JSON representation. It does not control GPIO, BLE, or Android.
This is a prototype risk-estimation and alert system. It does not diagnose injury or
dehydration.
